# Microphone handoff and iPhone playback volume

Reported on an iPhone 13 Pro Max running iOS 26.6.1: after microphone use, English World's recorded voice becomes roughly 80–90% quieter and stays quiet in both Safari and Chrome. The user reproduced the drop again while Safari Web Inspector was attached on 7 November. The app does not lower the voice player's volume during a conversation; its automatic ducking affects ambient sound only.

In a fresh Safari comparison on 7 November, the user reported that manual-only microphone entry still lowered the volume while automatic entry stayed normal. At the user’s request, automatic entry is now the sole normal workflow and the old setting is retired, including saved `autoListen:false` preferences. The microphone button still retries/finishes an answer, and typing remains available. This choice follows that observed comparison; it does not prove the physical cause or establish a general iOS volume fix.

On 8 November the user reported that the installed Home Screen app still sometimes became quiet and repeated an audible sentence prefix. A later baseline run on the same phone did not reproduce either symptom. Automatic listening and the previous category-recovery attempt therefore do not establish a physical-phone fix. The opt-in comparison at `/zaisti?audioDebug=1` tests the same recording through HTMLAudio and Web Audio before and after microphone use. See [AUDIO-DIAGNOSTICS.md](AUDIO-DIAGNOSTICS.md). Do not describe desktop tests or the diagnostic itself as a volume fix.

The likely failure is a native capture/playback route left behind by speech recognition. This is an inference, not a measured diagnosis from the affected phone. WebKit documents persistent lower playback volume after microphone use in [bug 236219](https://bugs.webkit.org/show_bug.cgi?id=236219). Its [category override implementation](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/audio/AudioSession.cpp) also ignores assigning the same override again, so a DOM value of `playback` alone does not prove that reapplying it repaired the native session.

`src/convo/audioFocus.ts` owns capture leases. Playback waits for recognition's actual `onend`, with the existing 1.2-second bound for engines that omit it. The timeout releases the wait; it does not consume a later real end event. A newer recognizer retains capture ownership.

The old player forced an `auto` → `playback` category cycle at the first `playing` event of every recording after any microphone use. A late recognizer end could do the same thing mid-sentence. Mechanical regressions reproduced both category writes while the player was already active. Apple documents that [changing the category of an active audio session immediately changes its route](https://developer.apple.com/documentation/avfaudio/avaudiosession/setcategory(_:)); that makes the old behavior a concrete restart risk. It is not proof of the affected phone's acoustic cause.

The first correction confined category recovery to an idle start and consumed it once per capture. Active output holds the route. A late recognizer end marks recovery pending; it neither changes the current sentence's category nor triggers a reset when that output's cleanup runs. First and repeated `playing` events never change category. This removed a mechanically reproduced restart risk, but did not resolve the user's physical-device volume problem.

The follow-up on the freshly reopened installed app was more specific: “Pretty good, thanks!” played normally, then the next recorded question became quiet, and later conversations stayed quiet until the app was force-closed. These are separate clips within one NPC turn. `Session.play` does not reopen the microphone between them. Four actual Mia recordings have mean levels within 0.1 dB, so there is no matching recording-level cliff. The exact native timing remains unmeasured; do not infer it from the DOM category getter.

Recorded playback now uses the existing persistent Web Audio context on iPhone/iPad (including iPad's desktop user agent). This avoids HTMLAudio play/pause and source replacement at every sentence boundary after recognition. The upstream [SpeechRecognition report](https://bugs.webkit.org/show_bug.cgi?id=321436) describes media-element conflicts on iOS 26.6, including installed apps; a [reporter in the Web Speech issue](https://github.com/WebAudio/web-speech-api/issues/96) and [WebKit volume-bug comment 16](https://bugs.webkit.org/show_bug.cgi?id=236219#c16) report avoiding related failures with Web Audio. These are supporting reports, not proof that the same cause or workaround applies to this phone.

The iOS path fetches the same authenticated MP3, decodes it with an offline context, and plays its unmodified normal-speed PCM at the existing requested gain. It uses no gain boost, extra microphone, silent media element, additional provider, or automatic HTML fallback. A real tap creates/resumes the shared context before asynchronous loading. Download/decode/resume failures keep the line pending with the existing Retry, Continue reading and explicit browser-voice choices. An interrupted or hidden output stops at its actual context-clock offset; a later tap resumes there instead of replaying the prefix. Only a source end whose rendered clock has reached the end completes a line. Stale asynchronous completion cannot resurrect canceled playback.

Slower speech remains at 0.82 speed without lowering the speaker's pitch. A bounded offline waveform-similarity overlap-add helper stretches the PCM once, then playback stays at rate 1. Normal and slow decoded buffers share a 24 MiB cache budget. The helper caps inputs at 60 seconds; the current 39,218-recording catalogue's maximum is 11.91 seconds. Four actual Mia clips retained identical local transcriptions and changed RMS by less than 0.3 dB after stretching. These desktop checks do not establish mobile CPU cost or subjective quality for every recording. Other platforms retain their existing gesture-authorized HTMLAudio path; explicit diagnostic A remains HTMLAudio so the original comparison remains available.

Capture stays on `auto`. Explicit `play-and-record` has helped some getUserMedia cases, but recent SpeechRecognition reports also describe recognition failures with that setting ([bug 321436](https://bugs.webkit.org/show_bug.cgi?id=321436)). This recovery attempt does not change recognition's capture category.

Checks:

- Relevant checks for this audio-only change: `npm run typecheck`, `npm test`, `npm run build`.
- `npm run check:content` is the separate full dialogue/fuzz sweep. It was stopped after partial successful output because this change does not modify content; it is not recorded as a full pass.
- `tests/audio-focus.test.ts` models a stale native category behind an unchanged DOM value, deferred late ends, idempotent output ownership, one-shot recovery, and a newer capture that must keep ownership.
- `tests/audio.test.ts` exercises repeated captures, delayed initialization/media start, unchanged volume and playback position, cancellation, retries and the same persistent player.
- `tests/audio-buffer.test.ts` exercises iOS/iPad selection, no HTML media priming, two consecutive post-microphone recordings, exact normal PCM and gain, offset recovery, early end rejection, hidden-page recovery, cancellation during decode/resume, repair versions, offline reuse, slow pitch and visible failure.
- `tests/time-stretch.test.ts` checks speech fundamentals, duration, silence, transients, stereo alignment, amplitude bounds and bounded work.
- `tests/browser/mobile-audio.mjs` uses a real repository recording and real media decoding in Chromium and WebKit, online and offline. It plays consecutive recordings after one tap with simulated recognition handoffs, including an end later than the fallback. Modeled category setters establish that late recovery is deferred while real media is active and applied before the next recording.
- `tests/browser/ios-buffer-audio.mjs` exercises actual MP3 decoding and AudioBuffer playback through the iOS branch in Chromium/WebKit, normal/slow, online/offline, two post-microphone sentences, late native-end simulation, and actual context suspension followed by a tap to resume the exact offset.

Desktop WebKit with a mobile viewport cannot measure the iPhone's physical speaker route or loudness. The affected phone still needs the controlled before/after comparison; the automated results establish lifecycle behavior and real recording completion, not a physical-device volume measurement.
